# Registro de decisiones (ADR)

Cada decisión o suposición que se aparta del prompt maestro, o lo precisa, queda aquí.

## Fase 0 — Esqueleto

1. **Versiones.** Java 21 LTS + Spring Boot 4.1.1 (Spring Framework 7, Spring Security 7, Hibernate 7, Jackson 3) + Angular 19 + PrimeNG 19 + Tailwind 4. El prompt pedía Boot 3.5.x; el equipo eligió Boot 4.1.1 manteniendo Java 21 (Boot 4 lo soporta). La versión de Java es la misma en `pom.xml`, `Dockerfile` y CI.
2. **Monorepo.** `backend/`, `frontend/`, `docs/`, `docker-compose.yml`, `.github/workflows/ci.yml`.
3. **Errores.** `GlobalExceptionHandler` único con `ProblemDetail` (RFC 9457). Nunca se expone `ex.getMessage()` de excepciones técnicas.

## Fase 1 — Identidad, tenancy y aprovisionamiento

### Correcciones a la Fase 0 encontradas al iniciar
4. `application.properties` contenía YAML (Spring lo leía como properties y se perdía la configuración). Se reemplazó por `application.yml`.
5. Había dos migraciones `V1` en `db/platform` (una era del tenant): Flyway no arranca así. La del tenant pasó a `db/tenant`. Como ninguna base llegó a migrarse (el arranque fallaba), se reescribieron `V1`/`V2` de plataforma en lugar de agregar `V3`.
6. En Boot 4 cambiaron paquetes y artefactos: `HibernatePropertiesCustomizer` está en `org.springframework.boot.hibernate.autoconfigure`; Testcontainers 2 usa `testcontainers-postgresql` y `org.testcontainers.postgresql.PostgreSQLContainer`; springdoc 3.x es la línea compatible con Boot 4.
7. `package.json` del frontend declaraba `primeng` y `@tailwindcss/postcss` pero el `package-lock.json` no los tenía (`npm ci` fallaba). Se regeneró con `npm install` y se commiteó (resuelto).

### Seguridad y tokens
8. **JWT HS256 con Spring Security OAuth2 JOSE (Nimbus)** en lugar de JJWT: se integra nativamente con `oauth2ResourceServer().jwt()`, valida firma, `exp` e `iss`, y evita la dependencia de JJWT con Jackson 2. La configuración es manual (sin autoconfiguración de resource server).
9. **Claims.** `sub` (usuario), `typ` (`platform`|`tenant`), `tid` (negocio, solo en tokens de negocio), `perms` (permisos del negocio), `padm` (solo superadmin). El tenant se toma **únicamente** de `tid`; no existe header de tenant.
10. **Token de plataforma vs. de negocio.** Los endpoints de negocio (`/api/v1/**` excepto `auth` y `tenants`) exigen la autoridad `TENANT_SESSION`, que solo tiene un token con `tid` → un token de plataforma recibe **403**. Además cada endpoint declara `@PreAuthorize("hasAuthority('recurso:acción')")`.
11. **Sin tenant en contexto**, Hibernate usa una conexión con `search_path = platform`, donde no existen tablas de negocio: una consulta de negocio sin tenant falla en lugar de caer en otro negocio. No hay "tenant por defecto".
12. **Refresh token.** Opaco (32 bytes aleatorios), guardado como SHA-256, rotado en cada uso, con detección de reutilización (si llega un token ya rotado se revocan todas las sesiones del usuario). La sesión de plataforma (antes de elegir negocio) también tiene refresh (`tenant_id` nulo). Al seleccionar negocio se revoca el refresh anterior.
13. **Ruta de la cookie `Path=/api/v1/auth`** (el prompt decía `/api/v1/auth/refresh`): logout y select-tenant también necesitan leer la cookie para revocarla. Sigue siendo `HttpOnly; Secure; SameSite=Strict`. `REFRESH_COOKIE_SECURE=false` solo si se sirve por HTTP en un host distinto de `localhost`.
14. **CSRF deshabilitado.** La API es stateless con Bearer; la única cookie es la de refresh, con `SameSite=Strict` y ruta limitada, y el refresh solo devuelve un access token al propio origen.
15. **Bloqueo por intentos fallidos:** 5 intentos → 15 minutos (`423 Locked`). Correo inexistente y contraseña errada devuelven el mismo mensaje y tiempo similar (hash señuelo) para no revelar qué correos existen.
16. **Rate limiting** en memoria por IP para login (10/min) y registro (5/min), configurable. Suficiente con una instancia; en Fase 7 se moverá a Redis o al proxy.
17. **Registro** crea el usuario en `ACTIVE`. La verificación por correo (`PENDING_VERIFICATION`) queda para Fase 7.
18. **Contraseñas** con `DelegatingPasswordEncoder` (BCrypt por defecto, permite migrar a Argon2 sin romper hashes). Política mínima: 10 caracteres con letras y números.
19. **Revocación de acceso**: un miembro desactivado o una membresía revocada dejan de poder elegir negocio o refrescar inmediatamente; un access token ya emitido sigue vigente hasta 15 min (TTL corto a propósito). El estado del negocio se cachea 30 s.

### Multi-tenancy
20. **Validación del modelo JPA (`ddl-auto=validate`).** Hibernate valida usando `getAnyConnection()`, que apunta a un schema plantilla `tenant_template` (migrado con `db/tenant` al arrancar). Así se validan las entidades de negocio sin elegir un negocio real. `tenant_template` no cumple el patrón `t_*`, por lo que nunca puede usarse como tenant.
21. **Orden de arranque.** Flyway se ejecuta de forma programática (`DatabaseMigrator`): `platform` → `tenant_template` → todos los negocios `ACTIVE`. Un `BeanFactoryPostProcessor` hace que el `entityManagerFactory` dependa de él, de modo que Hibernate valida sobre schemas ya migrados. Por eso no se usa `spring-boot-starter-flyway`.
22. **Nombres de schema en SQL.** Todo nombre pasa por `TenantSchemas` (slug `^[a-z][a-z0-9_]{2,40}$`, schema `^t_[a-z][a-z0-9_]{2,40}$`) antes de concatenarse. La tabla `platform.tenants` tiene además `CHECK` sobre el slug y `schema_name = 't_' || slug`.
23. **Consultas de acceso en JDBC con schema calificado** (`t_x.member_roles`…) al emitir tokens: en ese momento la petición aún no tiene tenant en contexto.
24. **Datos base en Flyway** (`db/tenant/V2__seed…`): permisos, 6 roles por defecto, sede `PRINCIPAL`, caja `CAJA-1` y ajustes del negocio. Son iguales en todos los negocios y quedan versionados. Solo el miembro dueño se siembra por código. Los IDs sembrados son UUID fijos (cada negocio tiene su propia copia).
25. **Semillas de módulos futuros** (métodos de pago, impuestos IVA 19/5/0, unidades, consumidor final, lista General, secuencias) se agregan como migraciones `db/tenant` en la fase de su módulo (3 y 5), para no crear tablas antes de que existan sus entidades.
26. **Aprovisionamiento fallido:** `DROP SCHEMA … CASCADE`, estado `FAILED` con `failure_reason` (solo el tipo de error; el detalle va al log) y respuesta `503`. Solo el dueño puede reintentar (`POST /api/v1/tenants/{id}/retry-provisioning`); a otros usuarios se les responde 404 para no revelar que existe.
27. **Tipos de negocio:** solo `RETAIL` se puede crear en el MVP (los demás responden 422).
28. **Aplazado a fases siguientes:** `plans`/`subscriptions` (Fase 7), catálogo DIVIPOLA `departments`/`cities` (Fase 2; mientras tanto las sucursales guardan `city_code` de 5 dígitos), invitación de miembros (Fase 2).

### Resultado del primer build real (2026-10-01)
La fase se escribió en un entorno sin acceso a Maven Central, npm ni Docker Hub, así que la primera compilación real fue en local (Windows, Docker Desktop):
- Compiló sin errores con Spring Boot 4.1.1 y la aplicación arrancó: la validación del modelo (`Instant` ↔ `timestamptz`) y springdoc 3.0.0 no dieron problemas.
- 20 de 21 tests pasaron a la primera. El fallo era del test, no del código: en Spring 7, `jsonPath("$[?(@.id == '…')].status").value(List.of(...))` devolvía `null`. Se reemplazó por `JsonPath.read` + AssertJ.

29. **Advertencias del IDE:** se desactivó `java.compile.nullAnalysis.mode` en `.vscode/settings.json`: con las anotaciones JSpecify de Spring 7, el análisis de nulos de JDT genera avisos falsos. No afecta a Maven ni al CI. Se reemplazaron también las APIs deprecadas en Spring 7 (`HttpStatus.UNPROCESSABLE_ENTITY` → `UNPROCESSABLE_CONTENT`).
30. **Entrega por parches:** durante la Fase 1 el asistente no tenía permiso de push al repositorio; los cambios se entregaron como archivos `.patch` (aplicados con `git am`) y el push lo hizo el equipo. Los `.patch` no se versionan.

## Fase 2 — Acceso y organización

31. **Invitaciones por enlace** (decisión del equipo). El administrador genera un enlace y lo comparte a mano (WhatsApp, correo); el envío automático por correo llega en la Fase 7. El token (32 bytes aleatorios) se entrega una sola vez y se guarda como SHA-256; vence en 7 días. La invitación vive en `platform.invitations` porque se consulta antes de que exista el miembro; roles y sucursales se guardan como IDs del schema del negocio (sin FK entre schemas) y se validan al crear y al aceptar.
32. **Aceptar exige iniciar sesión con el mismo correo** de la invitación (403 si no coincide). Si la persona no tiene cuenta, se registra y vuelve al enlace (`returnUrl`, solo rutas internas para evitar redirecciones abiertas).
33. **Token de invitación en el cuerpo**, no en la URL de la API (`POST /invitations/preview|accept`), para que no quede en logs de acceso. La vista previa es pública y tiene límite de peticiones.
34. **Una sola invitación pendiente por correo y negocio** (índice único parcial). Si la anterior venció, se revoca sola al invitar de nuevo; si sigue vigente, 409 (hay que revocarla para generar otro enlace).
35. **Anti-escalada de privilegios.** Nadie puede otorgar, quitar ni editar permisos que no tiene (al crear/editar/eliminar roles, invitar o cambiar roles de un miembro), comparando con los permisos de su token. Además: el rol OWNER no se asigna ni se edita, el propietario del negocio no se modifica y nadie se modifica a sí mismo. Así un rol personalizado con `members:manage` no puede convertir a nadie en ADMIN.
36. **Roles de sistema**: no se eliminan ni cambian de código; sus permisos sí se pueden ajustar (excepto OWNER). Los roles personalizados solo se eliminan si nadie los tiene asignados. Cuando en fases futuras se agreguen permisos, la migración que los cree debe otorgarlos también a OWNER (y ADMIN).
37. **Cambios de permisos y desactivación.** Los permisos van en el access token (15 min): un cambio de rol aplica en la siguiente renovación. Desactivar un miembro revoca sus refresh tokens de ese negocio, así que deja de poder renovar o volver a entrar; su access token vigente expira solo.
38. **Membresía vs. miembro.** Desactivar marca `members.active = false` (la membresía de plataforma sigue `ACTIVE`); select-tenant y refresh exigen ambas cosas. Re-invitar a un miembro desactivado lo reactiva con los roles nuevos.
39. **Ajustes tipados.** `GET/PUT /settings` usa un DTO con todos los campos en lugar de clave/valor libre: validación clara y contrato estable para el frontend. Se guardan en `business_settings` (clave/valor). Solo se admite la moneda COP por ahora. `BusinessSettingsApi` es la lectura para ventas e inventario.
40. **Sucursales y cajas.** El código no cambia después de creado. Siempre debe quedar al menos una sucursal activa. Desactivar en lugar de borrar. En Fase 5 se impedirá desactivar una caja con sesión abierta.
41. **DIVIPOLA parcial.** El entorno donde se escribió la fase no tenía acceso a internet, así que se sembraron los 33 departamentos y las 32 capitales (códigos verificables por patrón `xx001`) en vez de inventar códigos. El listado completo (~1.120 municipios) se cargará con una migración `V4` generada desde el archivo oficial del DANE/datos.gov.co. Las sucursales validan `cityCode` contra el catálogo (422 si no existe).
42. **Auditoría.** `audit_log` registra creación/cambio de sucursales, cajas, roles, miembros, invitaciones y ajustes, con antes/después en JSON (sin secretos ni tokens), actor e IP, en la misma transacción del cambio.
43. **Frontend.** Tabla genérica tipada `DataTableComponent<T>` con paginación del servidor; selects y listas de casillas nativos (estilo Tailwind) para evitar dependencias extra; diálogos y confirmaciones con PrimeNG. Ocultar botones por permiso es solo UX: el backend valida todo.

## Fase 3 — Catálogo y terceros

44. **Listas de precios** (decisión del equipo): la lista *General* es el precio del producto (`products.sale_price`) y de sus presentaciones; las demás listas guardan precios propios por producto y unidad en `price_list_items`. Si una lista no tiene precio para una unidad, se usa la General. El cliente sin lista usa la General (`customers.price_list_id` nulo).
45. **Todos los códigos de barras en una tabla** (`product_barcodes`, únicos en el negocio) con `unit_id` opcional: nulo = unidad base; si no, identifica una presentación. El prompt proponía `products.barcode` + `product_barcodes` + `product_unit_conversions.barcode`; una sola tabla garantiza unicidad global con una sola restricción y simplifica el lector.
46. **Códigos internos EAN-13** (decisión del equipo) con prefijo 29 (rango 20–29 reservado para uso interno en tienda) + secuencia por negocio + dígito de control. Se marcan `internal` para imprimir etiquetas más adelante.
47. **Edición de producto por reemplazo completo** (`PUT` con presentaciones, códigos y precios por lista). Internamente se compara con lo existente (actualiza, quita, agrega) en lugar de borrar y reinsertar, para no chocar con las restricciones únicas por el orden de escritura de Hibernate.
48. **Precios de presentación**: si la presentación no tiene precio propio, se calcula precio base × factor (redondeo HALF_UP a 2 decimales).
49. **Importación CSV** (decisión del equipo): todo o nada, validación previa (`dryRun`), actualización por SKU (las columnas ausentes conservan el valor actual), categorías nuevas creadas automáticamente (por nombre, sin distinguir mayúsculas), máximo 5.000 filas y 5 MB, UTF-8 obligatorio (Excel: *CSV UTF-8*). El separador se detecta (`;` en Excel en español). Números: un único separador seguido de exactamente 3 dígitos es de miles (`2.500` = 2500), si no es decimal (`2,5`). El lector CSV es propio (RFC 4180) para no agregar dependencias.
50. **Imágenes de producto**: fuera de esta fase (decisión del equipo).
51. **Impuestos**: tarifa 0 solo para tipos Exento/Excluido (evita confundir "IVA 0 %" con exento). El tipo no cambia después de creado; la tarifa sí (aplica a ventas futuras). No se desactivan impuestos, unidades ni categorías que usan productos activos.
52. **Terceros**: un documento = un tercero; puede ser cliente y proveedor (roles en `customers` y `suppliers`). Registrar como cliente un documento que ya es proveedor reutiliza el tercero y actualiza sus datos. Persona jurídica exige NIT; el DV del NIT se valida con el algoritmo de la DIAN. *Consumidor final* (CC 222222222222) es tercero del sistema y no se modifica.
53. **Permisos**: el CAJERO puede registrar clientes en caja (`parties:manage`, sembrado en Fase 1) pero no administra productos; el BODEGUERO administra productos pero no ve terceros.
54. **Búsquedas con LIKE** escapan `%`, `_` y `\` con `escape '\'` explícito (Hibernate/PostgreSQL no usan escape por defecto).
55. **Peticiones con booleanos opcionales** usan `Boolean` (no `boolean`): con Jackson 3 un primitivo ausente en el JSON puede rechazarse.

## Fase 4 — Inventario

56. **Costo promedio ponderado** (decisión del equipo), uno por producto para todo el negocio, guardado en `products.cost` (2 decimales, HALF_UP). Cada entrada con costo (saldo inicial, ajuste de entrada con costo; en Fase 7, compras) calcula `(existencia total × costo actual + cantidad × costo de entrada) / (existencia total + cantidad)`; si la existencia total es ≤ 0, el costo nuevo es el de la entrada. La existencia total se suma bajo el bloqueo del producto.
57. **Costo manejado por el inventario**: desde el primer movimiento `products.cost_locked = true` y el costo deja de editarse a mano (422) y por CSV (se conserva). Tampoco cambia la unidad base, porque saldos y kardex están en esa unidad.
58. **Salidas, traslados y conteos se valoran al costo promedio** y no lo cambian. Un ajuste de entrada sin costo entra al promedio actual.
59. **Conteo físico** (decisión del equipo): el documento guarda esperado (saldo bloqueado al registrar) y contado por línea; la diferencia se registra como `ADJUSTMENT_IN` o `ADJUSTMENT_OUT`. Sin diferencia no hay movimiento.
60. **Traslados inmediatos** (decisión del equipo): `TRANSFER_OUT` y `TRANSFER_IN` en la misma transacción; no hay estado "en tránsito".
61. **Inmutabilidad en la base de datos**: triggers que rechazan `UPDATE`/`DELETE` en `stock_movements`, `inventory_documents` e `inventory_document_lines`, además de `@Immutable` en JPA. Las correcciones se hacen con un nuevo ajuste.
62. **Orden del kardex** por `entry_no` (identidad de la base de datos), no por fecha: dos movimientos en el mismo instante quedan en el orden en que se registraron. Cada movimiento guarda `balance_after`.
63. **Concurrencia**: `StockLedger` es el único punto que modifica saldos. Bloquea en orden fijo, primero productos (los que recalculan costo o aún no tienen el costo manejado por el inventario) con `FOR NO KEY UPDATE`, y luego saldos (producto, sucursal) con `FOR UPDATE`. `FOR NO KEY UPDATE` no choca con los bloqueos de llave foránea que toma PostgreSQL al insertar movimientos, lo que evita interbloqueos. Si aun así hay uno, la API responde 409 para reintentar.
64. **Sin existencias negativas** desde documentos de inventario (422 *Existencias insuficientes*). El parámetro para permitir negativos llegará con ventas (Fase 5).
65. **Idempotencia**: `Idempotency-Key` opcional (8–100 caracteres `A-Z a-z 0-9 _ -`) en los `POST` que crean documentos; la misma clave devuelve el mismo documento. El frontend genera una por pantalla de edición.
66. **Límites**: hasta 500 líneas por documento, sin productos repetidos; cantidades > 0 (≥ 0 en conteos); decimales solo si la unidad base los admite. Costos unitarios con 2 decimales.
67. **Lotes**: `stock_balances.lot_id` existe para la Fase de lotes y vencimientos; hoy todos los saldos son sin lote.
68. **Sucursales por usuario**: `member_branches` aún no restringe las operaciones de inventario; cualquier usuario con el permiso opera en todas las sucursales. Se aplicará cuando la caja lo necesite (Fase 5).

## Fase 5 — Caja y ventas

69. **Medios de pago** (decisión del equipo): efectivo, tarjeta (datáfono externo, referencia opcional) y transferencia (Nequi, Daviplata, bancos), con pago mixto. Sembrados en `payment_methods` (V7); su administración queda para después. El crédito a clientes (cartera) es una fase posterior.
70. **Cierre ciego** (decisión del equipo): sin el permiso nuevo `cash:audit` (dueño, administrador y contador) el informe no muestra el esperado, la diferencia ni el desglose del efectivo ni el cobro por medio de pago. El cajero sí ve su lista de movimientos (necesaria para verificar lo registrado). V7 además **quita `cash:read` al rol Cajero**: ve solo sus sesiones, no las de los demás.
71. **Tiquete POS interno** (decisión del equipo) numerado `POS-n` desde `document_sequences` con la fila bloqueada: si la venta falla, el incremento se deshace (sin huecos). Un solo consecutivo por negocio; el prefijo y los rangos por resolución DIAN llegan con la facturación electrónica. El tiquete dice "Comprobante interno de venta".
72. **La venta exige caja abierta del usuario** (prompt). El rol Vendedor no tiene `cash:operate`, así que ve la pantalla de venta pero no puede cobrar; la preventa (vendedor arma, cajero cobra) queda para después.
73. **Precios del servidor**: precio por cliente (lista de precios, si no la General), impuesto del producto y descuento por línea (0–100 %). Si el precio de una línea o el total que mostró la pantalla difieren → 409 con el detalle. El frontend replica el cálculo (`sale-math.ts`) para mostrar el total; el servidor manda.
74. **Redondeo**: dinero a 2 decimales HALF_UP por línea (bruto, descuento, base, impuesto); con IVA incluido, base = total / (1 + tarifa) e impuesto = total − base. Los totales de la venta son la suma de las líneas. Se guardan totales por impuesto (`sale_tax_totals`).
75. **Descuentos**: por línea. Por encima de `max_discount_percent` (0 por defecto) exigen `sales:discount` → 403.
76. **Cambio solo en efectivo**: tarjeta + transferencia ≤ total; la suma de pagos ≥ total. Se guarda lo entregado (`tendered`) y lo aplicado (`amount`); a la caja entra el efectivo neto.
77. **Orden de bloqueos** (igual en todo el sistema, sin interbloqueos): venta (solo al anular) → sesión de caja `FOR SHARE` (el cierre toma `FOR UPDATE` y espera a las ventas en curso; una venta que llega después del cierre ve la sesión cerrada) → productos y saldos de inventario (`StockLedger`) → consecutivo `FOR UPDATE`.
78. **Idempotencia**: `Idempotency-Key` obligatoria en `POST /sales` (índice único). Repetirla devuelve la misma venta; si dos llegan a la vez, la segunda choca con el índice y devuelve la primera. Una clave usada por otro usuario → 409. En movimientos de caja es opcional y funciona igual.
79. **Anulación**: no se borra nada; estado VOIDED con motivo, `SALE_VOID` devuelve el inventario al costo promedio vigente (no recalcula el promedio; el reverso se permite aunque el producto se haya desactivado) y `SALE_VOID` de caja sale de la sesión original si sigue abierta o, si no, de la sesión abierta de quien anula (si no tiene, 422).
80. **Inmutabilidad en la base de datos**: triggers en `sales` (solo COMPLETED → VOIDED con sus campos de anulación), `sale_items`, `sale_payments`, `sale_tax_totals`, `cash_movements` y `cash_sessions` (solo OPEN → CLOSED; una sesión cerrada no cambia).
81. **Sucursales asignadas**: abrir caja exige que la caja sea de una sucursal del usuario (`member_branches`), salvo con `branches:manage`.
82. **Evento `SaleCompleted`/`SaleVoided`**: se publican dentro de la transacción (Spring `ApplicationEventPublisher`). La emisión electrónica futura los escuchará con `@TransactionalEventListener(AFTER_COMMIT)`.
83. **Pantalla de venta fuera del menú lateral** (`/pos`) para aprovechar la pantalla en tablet horizontal. El ancho del papel (58/80 mm) es una preferencia del equipo guardada en el navegador, no un ajuste del negocio.
84. **E2E**: proyecto aparte `e2e/` con `@playwright/test` 1.56.0 (para no tocar el lockfile del frontend). Corre contra la app levantada con docker compose; en GitHub Actions es un flujo manual (no bloquea los PR).

## Fase 6 — Reportes y dashboard

85. **Reportes incluidos** (decisión del equipo): además de ventas por rango, sucursal, vendedor y medio de pago, productos más vendidos y por categoría, utilidad (margen), impuestos e inventario valorizado.
86. **Modelo de lectura**: el módulo `reporting` consulta con SQL nativo (solo lectura) las tablas de ventas, catálogo, inventario y caja del negocio, sin pasar por los servicios de esos módulos. Es la excepción a "los módulos se hablan por interfaces": agrega datos de varios módulos y nunca escribe.
87. **Qué cuenta**: solo ventas COMPLETED; las anuladas se informan aparte (cantidad y total) en el resumen. Las fechas son las de registro de la venta en la zona horaria del negocio; la anulación no cambia la fecha de la venta.
88. **Utilidad** = base (sin impuestos ni descuentos) − costo de lo vendido, con el costo promedio que quedó guardado en cada línea al vender (no el costo de hoy). Margen = utilidad / base.
89. **Inventario valorizado**: existencias actuales × costo promedio actual del producto, por sucursal. El valor a una fecha pasada queda para después (requiere reconstruir saldos desde el kardex).
90. **Rango máximo** de 367 días por consulta (un año completo comparable) para acotar el costo de las consultas.
91. **Gráficas sin librerías** (decisión del equipo, revisable): barras con HTML/CSS en un único componente `app-bar-chart`; cambiar a una librería (p. ej. Chart.js) solo toca ese componente.
92. **Tablero**: con `reports:read` se ve el del negocio; sin él pero con `sales:read` (cajero, vendedor) se ven "Mis ventas de hoy". El bodeguero no ve ventas.
93. **CSV para Excel en español** (decisión del equipo): `;`, coma decimal, sin separador de miles, UTF-8 con BOM. Los textos que empiezan por `= + - @`, tabulador o retorno llevan `'` delante (inyección de CSV). El detalle de ventas admite hasta 100.000 filas; si el rango tiene más, responde 422 pidiendo un rango más corto (no se corta en silencio).
94. **Índices** (`V8`): ventas COMPLETED por fecha (parcial), ventas por vendedor y fecha, líneas por venta y producto, pagos por medio y venta.

## Fase 7-1 — Producción y respaldos

156. **Servidor propio con `docker compose`** (Hetzner CX23/CAX11, 2 vCPU y 4 GB) en vez de PaaS o Cloud Run: el mismo modelo de contenedores que en desarrollo, costo fijo de ~€6/mes y sin arranques en frío de Java. Los planes de 1 GB no alcanzan (JVM + PostgreSQL + Caddy). PostgreSQL va en el mismo servidor; pasar a una base gestionada después solo cambia `DB_URL`.
157. **Caddy como única entrada** (imagen `pos-hibrido-web`: build de Angular + Caddy): HTTPS automático con Let's Encrypt, archivos estáticos y `/api/*` hacia el backend en el **mismo dominio**, así la cookie de refresh `SameSite=Strict` funciona sin CORS (igual que el proxy de `ng serve`). Sin nginx aparte. Solo Caddy publica puertos; `/actuator` y Swagger no se exponen (solo `/healthz` → `/actuator/health`, sin detalles).
158. **Cabeceras de seguridad en Caddy**: HSTS (sin `includeSubDomains`, para no afectar otros subdominios del dominio), `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` (la ruta `/invitacion/:token` no se filtra a otros sitios), `Permissions-Policy` y **CSP** `script-src 'self'`. `style-src` necesita `'unsafe-inline'` porque PrimeNG y Angular insertan `<style>` en tiempo de ejecución. Para cumplir la CSP: el script anti-parpadeo del modo oscuro pasó de `index.html` a `public/theme-init.js`, y se apagó `inlineCritical` (Angular cargaba el CSS con `onload="this.media='all'"`, un manejador en línea que la CSP bloquea y dejaría la app sin estilos).
159. **Caché**: archivos con huella en el nombre (`main-ABCD1234.js`) con `immutable` por un año; todo lo demás (`index.html`, `theme-init.js`) con `no-cache` para que una versión nueva se vea al recargar. Solo las rutas sin extensión caen en `index.html`: un archivo con extensión que no existe (un *chunk* de otra versión tras volver atrás) da 404, para que el navegador no guarde HTML por un año en la URL de un `.js`.
160. **IP real detrás del proxy**: `server.forward-headers-strategy=native` (variable `FORWARD_HEADERS_STRATEGY`, solo en producción). Tomcat acepta `X-Forwarded-For/-Proto` solo de redes privadas (la red de Docker) y Caddy ignora el `X-Forwarded-For` que mande el cliente. Sin esto, el límite de intentos de login sería uno solo para todos los usuarios (todos llegarían con la IP de Caddy) y la auditoría registraría la IP del proxy. Por lo mismo, **sin registro AAAA**: la red de Docker es solo IPv4 y las conexiones IPv6 llegarían todas con la IP interna del puente.
161. **Dos usuarios de PostgreSQL**: el superusuario (`POSTGRES_ADMIN_USER`) solo para respaldos y administración; la app usa `DB_USER`, sin superusuario, como **dueño de la base** (puede crear los schemas `t_*` y migrarlos). Lo crea `deploy/postgres/initdb/01-app-user.sh` la primera vez. Se probó aplicando todas las migraciones (plataforma V1–V3 y negocio V1–V8, con triggers) con ese usuario.
162. **Imágenes construidas en GitHub Actions** (`images.yml`) y publicadas en ghcr.io para AMD y ARM: el servidor solo descarga (no compila Maven ni Angular con 4 GB). Se construyen en `main` **solo después de que el CI pasa** (`workflow_run`), con etiquetas `latest` y `sha-<commit>`, y con etiquetas de versión `v*` (`0.7.0`), recomendadas en producción para saber qué corre y poder volver atrás. Las etapas de compilación corren en la plataforma de quien construye (`$BUILDPLATFORM`), sin emular Maven en ARM.
163. **Backend**: jar extraído en dos capas (librerías y app) para descargas pequeñas al actualizar; `MaxRAMPercentage=70` según el límite del contenedor (1280 MB); `ExitOnOutOfMemoryError` (Docker lo reinicia en vez de quedar a medias); apagado ordenado (`server.shutdown=graceful`, 20 s) para que una venta en curso termine antes de detenerse; `HEALTHCHECK` con `/actuator/health`.
164. **Límites de memoria por contenedor** (PostgreSQL 1 GB con `shared_buffers=256MB`, backend 1280 MB, Caddy 256 MB, respaldos 512 MB) + 2 GB de swap, y rotación de logs de Docker (5 × 10 MB por servicio) para que el disco de 40 GB no se llene.
165. **Respaldos**: `pg_dump` en formato *custom* de toda la base (plataforma y todos los negocios), verificado con `pg_restore --list` antes de darlo por bueno, 7 copias en el servidor y copia **cifrada con rclone crypt** en Google Drive (scope `drive.file`: rclone solo ve lo que él crea). Retención en la nube: 30 días de diarios y ~13 meses de mensuales (la primera copia que se logre subir en cada mes). Contenedor propio con cron (`deploy/backup`), misma versión mayor de PostgreSQL (16).
166. **Prueba de restauración automática semanal** (`restore.sh --test`): restaura el último respaldo en una base aparte, revisa que cada negocio activo o suspendido tenga su schema y cuenta negocios, usuarios, productos y ventas, y la borra. **Restaurar en producción** (`--production`) exige el backend detenido, restaura en una base nueva, la revisa y solo al final la intercambia por la real; la anterior queda renombrada para volver atrás. Aviso opcional a healthchecks.io si un respaldo o una prueba falla o no corre.
167. **Saltos de línea LF obligatorios** (`.gitattributes`) para scripts y archivos de `deploy/`: con CRLF (copia de Windows), `sh` no los ejecuta y los contenedores no arrancan. La imagen de respaldos además quita los CR al construirse.

## Fase 7-2 — Auditoría completa

168. **Dos registros separados**: lo que pasa dentro de un negocio sigue en su `audit_log` (lo ve el negocio); lo que pasa antes de elegir negocio o afecta a la plataforma (inicios de sesión, intentos fallidos, bloqueos, refresh token reutilizado, límites superados, negocios creados) va en `platform.security_events` y lo ve solo el administrador de plataforma (consola de la Fase 7-3). Así un negocio no ve intentos fallidos de cuentas que también pertenecen a otros negocios (decisión del usuario).
169. **Creación del negocio**: se conserva `TENANT_PROVISIONED` (el dueño queda como miembro, sin datos, del sembrado) y se agrega `BUSINESS_CREATED` con razón social, nombre comercial, identificador y tipo. **Entrar y salir de un negocio** queda en ambos registros: `TENANT_ENTERED`/`LOGOUT` en la plataforma y `SESSION_STARTED`/`SESSION_ENDED` en el `audit_log` del negocio (el dueño ve quién entró y cuándo). La renovación del token cada 15 minutos no se registra (sería ruido). Cerrar sesión dos veces con la misma cookie no duplica el registro (`revoke` solo informa la sesión si seguía activa).
170. **Eventos de error sin segunda conexión**: el login (`noRollbackFor` 401, 423 y 403) y la selección de negocio (`noRollbackFor` 403) no revierten su transacción, y el evento se guarda en ella. Una transacción aparte (`REQUIRES_NEW`) por intento fallido pediría dos conexiones por petición: con muchos intentos a la vez (un ataque) podría agotar el pool de 10 conexiones y tumbar el login para todos. Solo `AuditLogger.logDetached` (exportaciones, sin transacción de escritura) usa `REQUIRES_NEW`.
171. **Correo del intento**: en `LOGIN_FAILED` con correo inexistente se guarda el correo escrito (normalizado, máx. 254), útil para ver ataques de diccionario; la respuesta al cliente sigue siendo la misma que con contraseña errada (sin enumeración de cuentas).
172. **`RATE_LIMITED` una vez por IP y ventana**: solo la primera petición rechazada de cada minuto se registra; un ataque sostenido deja un evento por minuto, no miles. Si la base no responde, el límite se aplica igual.
173. **Auditoría inmutable y para siempre** (decisión del usuario): trigger `BEFORE UPDATE OR DELETE` en `audit_log` (misma función `reject_ledger_change` de V6) y en `platform.security_events`. No hay purga; si algún día se necesita, es una tarea de base de datos (deshabilitar el trigger), no de la aplicación. Riesgo conocido: un ataque de login repartido en muchas IPs hace crecer `security_events` (~300 bytes por intento; un millón de intentos ≈ 300 MB). Si pasa, la salida es particionar la tabla por mes y archivar las particiones viejas.
174. **Permiso `audit:read`** para Dueño, Administrador y Contador (decisión del usuario), con su opción de menú en la sección Reportes. El contador revisa anulaciones, cierres de caja y cambios de precios.
175. **Exportar también se audita**: cada CSV de reportes (`REPORT_EXPORTED`) y de la auditoría (`AUDIT_EXPORTED`) queda con el nombre del archivo y las filas: son datos que salen del sistema.
176. **Etiqueta legible del registro** sin tocar cada módulo: la consulta toma el primer dato que identifique el registro de lo guardado antes o después (`name`, `number`, `code`, `email`, `tradeName`). Los nombres en español de acciones y módulos están en el frontend (`audit-labels.ts`) y en el backend para el CSV (`AuditLabels.java`); las acciones genéricas (`*_CREATED`, `*_UPDATED`, `*_ACTIVATED`…) se arman con verbo + sustantivo, así una acción nueva se ve bien aunque no esté en la lista.
177. **Detalle antes/después** en una tabla de tres columnas con lo que cambió resaltado (`bg-warning-soft` y texto para lectores de pantalla). En las creaciones solo hay "Valor". Los datos se devuelven como JSON real (`@JsonRawValue` sobre el texto de `jsonb`), sin volver a interpretarlos en el backend.
178. **Filtros de la auditoría** sin consultar otros módulos: `/audit/actions` y `/audit/actors` salen del mismo `audit_log`, así el contador (que no tiene `members:read`) puede filtrar por usuario. Sin fechas, el servidor y la pantalla usan los últimos 7 días.

## Fase 7-3 — Consola de plataforma, suspensión y límites

179. **Administradores de plataforma por configuración** (decisión del usuario): `PLATFORM_ADMIN_EMAILS` (correos separados por coma) se aplica **al arrancar** el backend sobre `platform.users.platform_admin`: las cuentas existentes con esos correos quedan como administradoras y, si la lista no está vacía, las demás dejan de serlo (sin lista no se toca nada; el permiso se puede dar a mano). No se compara el correo en cada inicio de sesión: el registro es abierto y sin verificación de correo, y quien se registrara primero con un correo configurado sería administrador. Procedimiento: registrarse, poner el correo y reiniciar el backend. El permiso va en el token al emitirlo (quitarlo tarda hasta la siguiente renovación, ≤ 15 min). Se avisa en el log de correos configurados sin cuenta.
180. **Eliminar un negocio = SUSPENDED** (prompt maestro): nunca se borra el schema desde la API. Columnas `suspended_at`, `suspended_by`, `suspension_reason` y `closed_by_owner` en `platform.tenants` (V5) con un CHECK que las ata al estado. `closed_by_owner` se guarda explícito (no se deduce de `suspended_by`: un administrador puede ser dueño de un negocio).
181. **Quién suspende** (decisión del usuario): el administrador suspende (motivo obligatorio, lo ven los miembros) y reactiva cualquier negocio; el dueño puede cerrar el suyo desde Ajustes, y solo el administrador lo reactiva. Cerrar exige escribir el nombre comercial y la **contraseña** del dueño (una sesión robada o un clic por error no bastan); los errores de confirmación son 422, no 401, para que el frontend no los tome como sesión vencida. Una contraseña errada queda como `TENANT_CLOSE_DENIED` y el intento cuenta en el límite de operaciones pesadas (20/min).
182. **Suspendido = nadie entra** (decisión del usuario): se revocan los refresh tokens de todos los miembros, el directorio de negocios se limpia ahora y otra vez al confirmar la transacción (si no, una petición concurrente podría guardar el estado anterior 30 s), y los access tokens vigentes reciben 403 con `code: TENANT_UNAVAILABLE`; el frontend cierra la sesión una sola vez, avisa y lleva al login (sin un toast por pantalla). En "Elegir negocio" aparece "Suspendido" con el motivo, o "Su dueño lo eliminó". Un refresh token **revocado pero no rotado** (cierre de sesión, suspensión) responde 401 simple: solo se trata como robo (`REFRESH_TOKEN_REUSED` y cierre de todas las sesiones) si el token ya había sido **rotado**. Antes, suspender un negocio hacía que cada miembro pareciera víctima de robo y perdiera sus sesiones en los demás negocios.
183. **La consola no entra a los negocios**: solo ve la ficha de `platform.tenants` (dueño, miembros activos, estado) y los eventos de seguridad; los datos de cada negocio siguen siendo de su dueño. La suspensión queda en la auditoría del negocio sin autor (aparece como "Sistema"), con `by: plataforma` o `dueño`.
184. **Límites de solicitudes en toda la API** (decisión del usuario, "moderados"): por usuario (claim `sub`) o por IP sin sesión, ventana fija de un minuto en memoria: 300 generales y 20 "pesadas" (CSV, importar productos, cerrar negocio, que además pide contraseña). Filtro después de autenticar y antes de autorizar. Un cajero con lector hace unas pocas solicitudes por venta, lejos del límite. Configurables (`RATE_LIMIT_API`, `RATE_LIMIT_HEAVY`); con varias instancias habría que moverlo a Redis o al proxy. El primer rechazo de cada ventana queda como `RATE_LIMITED` (con el usuario y `scope`).
185. **Consola fuera del shell de negocio** (`/plataforma`, con su propio encabezado): funciona con la sesión de plataforma, sin elegir negocio. Acceso desde "Elegir negocio" y desde el menú de usuario, solo si el token trae `padm`; el backend vuelve a exigirlo en cada petición.

## Fase 7-4 — Correos (Resend)

186. **Resend por su API HTTP** (`POST https://api.resend.com/emails`, cliente HTTP del JDK) y no por su SMTP: sin dependencias nuevas para producción, errores claros (429/5xx reintentables, 4xx no) y cabecera `Idempotency-Key` para que un reintento no duplique el correo. Plan gratis: 100 correos/día y 3.000/mes, suficiente al inicio. Sin dominio verificado Resend solo entrega desde `onboarding@resend.dev` al correo del dueño de la cuenta; para producción se verifica el dominio (SPF y DKIM en el DNS) y se usa `MAIL_FROM` con ese dominio.
187. **Tres formas de envío, elegidas al arrancar**: Resend con `RESEND_API_KEY`; SMTP si existe `spring.mail.host` (en desarrollo, **Mailpit** en `docker compose`: bandeja en `http://localhost:8025`, nada sale a internet; decisión del usuario "buzón de prueba local"); y si no hay ninguno, el texto del correo (con su enlace) va al log (útil para probar el modo producción en local; en el servidor los enlaces de un solo uso quedarían en el log, por eso Resend está en la lista de seguridad antes de abrir a clientes). Los tests usan un buzón en memoria (`RecordingMailSender`).
188. **Enviar después del commit, en segundo plano y con reintentos** (`TransactionSynchronization.afterCommit`, 2 hilos, 3 intentos a 0/2/8 s): si la transacción se revierte no sale un correo con un enlace que no existe, y un Resend lento o caído no frena ni tumba el registro, la invitación o la suspensión. El costo: si los tres intentos fallan, el correo se pierde (queda en el log); el usuario puede pedirlo de nuevo ("Reenviar correo", "Reenviar invitación", "¿Olvidaste tu contraseña?"). Una cola persistente se justifica con más volumen.
189. **Confirmar el correo antes de crear un negocio** (decisión del usuario): se puede iniciar sesión y aceptar invitaciones sin confirmar, pero `POST /tenants` responde 403 `EMAIL_NOT_VERIFIED`. Las cuentas que ya existían quedan confirmadas (V6 copia `created_at`). Aceptar una invitación y restablecer la contraseña también confirman el correo: ambas prueban que la persona recibe correo en esa dirección. `EMAIL_VERIFICATION_REQUIRED=false` lo apaga (solo para pruebas).
190. **Administradores de plataforma solo con correo confirmado**: `PLATFORM_ADMIN_EMAILS` se aplica solo a cuentas con `email_verified_at`. Cierra el riesgo de la decisión 179 sin depender del orden de los pasos: aunque alguien se registre primero con el correo del administrador, no puede confirmarlo.
191. **Enlaces de un solo uso** en `platform.user_tokens` (V6): 32 bytes aleatorios en Base64URL en el enlace; en la base solo el hash SHA-256 (un respaldo filtrado no sirve para entrar). Confirmar correo: 24 h; restablecer contraseña: 1 h. Pedir uno nuevo invalida los anteriores del mismo tipo; se consumen con `SELECT … FOR UPDATE` (dos clics simultáneos no lo usan dos veces). Respuesta única para inválido, vencido o usado (422 "El enlace no es válido o ya venció. Pide uno nuevo.").
192. **"¿Olvidaste tu contraseña?" no revela cuentas**: responde 204 exista o no el correo (y lo registra como `PASSWORD_RESET_REQUESTED`), máximo un correo por minuto por cuenta. Al restablecer: se desbloquea la cuenta, se cierran **todas** las sesiones (quien tenía la contraseña vieja pierde el acceso) y llega el aviso "Tu contraseña cambió" (decisión del usuario), para que el dueño real note un cambio que no hizo.
193. **Invitación por correo + enlace** (decisión del usuario): el correo sale al invitar y el enlace sigue apareciendo una vez en pantalla para compartirlo por WhatsApp si el correo no llega. "Reenviar" revoca la invitación y crea otra igual con enlace nuevo (el viejo deja de servir; nunca se guardan tokens en claro para volver a enviarlos) y se audita como `INVITATION_RESENT`.
194. **Aviso al dueño al suspender, reactivar o cerrar su negocio** (decisión del usuario), con el motivo. El administrador no puede "suspender en silencio" y el dueño se entera aunque no entre a la app.
195. **Plantillas en código** (`MailTemplates`), HTML con tablas y estilos en línea (lo que soportan los clientes de correo) + versión en texto plano; todo dato escrito por usuarios (nombres, motivos) se escapa en el HTML. Fechas en hora de Colombia. Los logs no guardan correos completos (`a***@dominio.com`).

## Fase 7-5 — CI y manual de uso

196. **Lint del frontend con ESLint + angular-eslint** (`npm run lint`, paso del CI antes del build): reglas recomendadas de ESLint, typescript-eslint y angular-eslint (plantillas incluidas), más `eqeqeq`, `no-console` (salvo warn/error) y accesibilidad básica de plantillas (`alt-text`, `valid-aria`, `role-has-required-aria`, `button-has-type`). Sin reglas de estilo: buscan errores reales, no discusiones de formato. Variables e imports sin usar son error; parámetros sin usar en callbacks, no. El backend no tiene lint aparte: compila con Java 21 y sus pruebas son la red.
197. **E2E en cada PR hacia `main`** (decisión del usuario): Playwright contra `docker compose up` (incluye Mailpit para confirmar el correo), con `concurrency` para cancelar la ejecución anterior del mismo PR. Si falla, se guardan los logs de los contenedores y el reporte de Playwright. Costo: ~10 minutos de Actions por PR (el plan gratis trae 2.000 min/mes en repos privados).
198. **Manual de uso público en `/manual`** (decisión del usuario: "página web compartible"): una ruta de la propia app, sin sesión, con la marca y el dominio del producto, para enviarla a clientes antes y después de comprar. Cada sección tiene enlace propio (`/manual#cobrar`, botón "Copiar enlace"), buscador sin tildes, glosario (el mismo de la ayuda en pantalla) e impresión limpia. El contenido vive en código (`manual-content.ts`) junto a las pantallas: se revisa en el mismo PR que cambia una pantalla y se publica con cada versión. La ayuda "?" de cada pantalla enlaza a su sección (abre en otra pestaña para no perder una venta en curso); una prueba verifica que esos enlaces existan.
199. **Al reactivar un negocio se migra su schema**, y al arrancar se migran los activos **y los suspendidos**. Antes solo se migraban los activos: un negocio suspendido durante una actualización volvía con tablas viejas hasta el siguiente reinicio. Flyway no hace nada si el schema ya está al día. Pendiente para la 7-6: con cientos de negocios, migrar uno por uno alarga cada arranque; se medirá y, si hace falta, se migrará en paralelo o en segundo plano.

## Fase 7-6 — QA completo

200. **QA en cuatro partes** (`docs/QA.md`): plan, matriz de riesgos y registro de hallazgos con id (SEG, DIN, INV, UI), severidad y estado. Cuatro revisiones de código de punta a punta (seguridad y aislamiento; dinero; inventario, concurrencia y operación; interfaz). **Riesgos aceptados** (7-6a): saber si un correo tiene cuenta por el 409 del registro y el 423 del bloqueo (SEG-10: el registro abierto lo necesita para explicar el error, y el límite por IP frena la enumeración masiva); el cajero ve los movimientos de venta de su sesión y podría calcular el esperado del cierre ciego (SEG-11: igual conoce sus ventas en "Mis ventas de hoy"; el cierre ciego evita el error de "ajustar" el conteo, no un cálculo deliberado).
201. **El Vendedor cobra con su propia caja** (decisión del usuario, V10): recibe `cash:operate`. Se diferencia del Cajero en que no registra clientes. Se descartó la "preventa" (vendedor arma el pedido, cajero cobra) por ser una función nueva.
202. **Aceptar una invitación ya no confirma el correo** (corrige la decisión 189): el token de la invitación también lo recibe quien invita (para compartirlo por WhatsApp), así que alguien podía registrarse con un correo ajeno, invitarse y aceptarse para darlo por confirmado y, con él en `PLATFORM_ADMIN_EMAILS`, heredar el permiso de administrador al reiniciar. Solo confirman el correo el enlace "Confirmar mi correo" y restablecer la contraseña (ambos llegan únicamente al correo).
203. **Límites por ruta normalizada**: los límites por IP y por usuario comparan la ruta decodificada y sin `;…` ni "/" final (como Spring Security y MVC), no `getRequestURI()`: `/auth/%6Cogin` evitaba el límite de 10 por minuto.
204. **Contador de intentos fallidos en una sola sentencia SQL** (`LoginAttemptStore`): con la entidad y su `@Version`, una ráfaga en paralelo contaba como un intento y los demás eventos se perdían. No se bloquea la fila antes de comparar la contraseña: un `FOR UPDATE` al leer haría esperar en fila (con conexión tomada y durante el BCrypt) a todos los intentos contra la misma cuenta, y un ataque agotaría el pool; el `UPDATE` solo retiene la fila un instante, después de comparar. Si "eliminar negocio" bloquea la cuenta, también queda `ACCOUNT_LOCKED`. Riesgos menores aceptados: el tope diario de invitaciones se cuenta sin bloqueo (una ráfaga puede pasarse por unas pocas), y en navegadores sin Web Locks la segunda pestaña que renueva a la vez vuelve al login (las demás sesiones ya no se cierran). La contraseña que piden otras acciones (eliminar el negocio) cuenta igual para el bloqueo.
205. **Renovación de sesión entre pestañas**: (a) el frontend renueva de a una por navegador con Web Locks (`REFRESH_LOCK`), así la segunda pestaña sale con la cookie nueva; (b) el servidor bloquea la fila del token al rotar y da un margen de 30 s en que reutilizar un token recién rotado responde 401 sin cerrar todas las sesiones; pasado el margen sigue siendo señal de robo. (c) Si al renovar la cookie es de **otro negocio** (se eligió otro en otra pestaña), la petición que falló no se repite —se guardaría en el negocio equivocado— y se avisa; (d) sin conexión o con el servidor caído, la sesión se conserva (antes se cerraba y se perdía el carrito).
206. **Invitaciones con espera y tope**: reenviar la misma invitación, una vez por minuto; máximo 50 invitaciones (nuevas o reenviadas) por negocio cada 24 horas. Cada una envía un correo con texto que escribe el negocio (su nombre): sin tope servían para spam y para agotar la cuota diaria de correos de todos. Volver a invitar a un miembro desactivado exige poder gestionarlo (igual que "Activar").
207. **Inicio sin la lista "Lo que puedes hacer en este negocio"** (pedido del usuario): repetía en texto lo que ya muestran el menú y los accesos rápidos. Solo queda un aviso cuando el usuario no tiene ningún permiso (el inicio quedaría vacío). El detalle técnico de permisos sigue en Roles y permisos.
208. **Pesos enteros** (decisión del usuario, QA DIN-2): el total de cada línea se redondea al peso (HALF_UP) con las mismas reglas en `SaleCalculator` y `sale-math.ts`: bruto y descuento al peso; con IVA incluido la base y el impuesto se separan del total con centavos (información tributaria) pero suman exacto; sin IVA, total = pesos(base × (1 + tarifa)) e impuesto = total − base. Pagos, base de apertura, conteo y movimientos de caja se rechazan con centavos (`@WholePesos`, 400 "Escribe el valor en pesos, sin centavos."; `10000.00` sí sirve). Las columnas siguen con 2 decimales (ventas anteriores intactas).
209. **Campo de pesos propio** (`appPesos`, QA DIN-1) en lugar de `<input type="number">` para todo monto: acepta "250.000", "$ 1.500" y "1.234,56", entrega un número y al salir del campo lo muestra con puntos de miles. `appPesos` sin valor = pesos enteros (caja, cobro, cupo); `appPesos="2"` = con centavos (precios y costos). Se prefirió a `p-inputNumber` para conservar los estilos, los `id` y el `select()` del cobro. Las cantidades siguen como `type="number"`.
210. **El informe de una caja cerrada no cambia** (QA DIN-3): anuladas, ventas netas y medios de pago se calculan con las anulaciones hasta el cierre; las posteriores (cuyo efectivo se devolvió en otra caja) se informan aparte.
211. **Egresos y retiros con tope** (QA DIN-4): no pueden superar el efectivo que debería haber; el mensaje no dice cuánto hay, para no romper el cierre ciego.
212. **"Hoy" es el día de Colombia** (QA DIN-6): los periodos rápidos, la auditoría y el filtro de fechas usan `businessToday()` (America/Bogota) y no la zona del equipo. Un rango de más de 367 días en la URL cae en el periodo predeterminado.
213. **Cobro más seguro en el POS**: (a) el diálogo de cobro no se cierra ni el carrito cambia mientras se registra la venta (QA UI-3); (b) el foco no se mueve si hay un diálogo abierto, y F4 espera a que lleguen las búsquedas de códigos pendientes (UI-4); (c) una ráfaga del lector (6+ caracteres a menos de ~35 ms) en el monto no registra la venta: se restaura el monto y se avisa (UI-2); (d) un error al consultar la caja muestra "Reintentar" en vez de "Abrir caja" (UI-5); (e) en el editor de productos, Enter en un campo no guarda (UI-1: el lector termina cada lectura con Enter).
214. **Un negocio con la migración rota no tumba a los demás** (QA INV-1, INV-4, INV-12): al arrancar se migran primero `platform` y `tenant_template` (si fallan, la app no arranca: son de todos) y luego los negocios en paralelo, de a 4 (`DatabaseMigrator`). Si uno falla, se registra en el log, queda marcado (`TenantMigrationFailures`) y `TenantDirectory` lo trata como no disponible (403 "El negocio no está disponible"); los demás entran normal. Al reactivarlo o migrarlo de nuevo con éxito, se desmarca. Flyway ya **no crea** el schema de un negocio que falta (solo el de la plantilla): antes lo recreaba vacío y escondía una pérdida de datos. Se migran de a 4 como máximo y nunca más de la mitad del pool. Las migraciones usan el pool, así que también tienen `lock_timeout` de 10 s: al arrancar no hay tráfico (no esperan bloqueos), y si una falla por eso el negocio queda marcado y se corrige reiniciando.
215. **`TRUNCATE` también está prohibido** en las tablas inmutables (QA SEG-12; tenant V11, platform V7): kardex, documentos de inventario, caja, ventas, auditoría y eventos de seguridad. Los triggers de fila no se disparan con `TRUNCATE`; ahora un trigger por sentencia lo rechaza con el mismo error que un `UPDATE`/`DELETE`.
216. **Límites de tiempo y errores claros con carga** (QA INV-6): esperar una conexión del pool máximo 10 s (`DB_CONNECTION_TIMEOUT_MS`), esperar un bloqueo máximo 10 s (`lock_timeout`) y una transacción abierta sin actividad se corta a los 60 s. Pool agotado o consulta vencida: **503** "El sistema está ocupado…" con `Retry-After: 5` (antes 500). Bloqueos y conflictos de concurrencia: 409; valores fuera de rango de la base: 422. Reportes, auditoría y verificación de inventario: transacción de solo lectura con máximo 60 s.
217. **Consultas pesadas con cupo** (QA INV-7, INV-11): exportar ventas una a una o la auditoría y verificar la consistencia del inventario comparten un cupo de **2 a la vez en todo el servidor** (`ExportGate`); quien llega con el cupo lleno espera hasta 10 s y si no, 429 "Hay muchos reportes pesados en curso…". El CSV se escribe directo en bytes (UTF-8 con BOM), sin una copia `String` intermedia. `/inventory/consistency` pide `inventory:adjust` (es soporte, no consulta del día a día). Las colecciones de productos se cargan por lotes de 100 (`default_batch_fetch_size`, QA INV-5) en lugar de una consulta por producto.
218. **El conteo físico compara con lo que había al empezar a contar** (QA INV-2): el editor envía en cada línea `expectedQuantity` (la existencia que mostró al agregar el producto). Si mientras se cuenta se vende, el ajuste es contado − mostrado y las ventas hechas durante el conteo siguen descontadas; antes se comparaba con el saldo al guardar y el conteo "devolvía" lo vendido. Sin `expectedQuantity` (clientes viejos de la API) se usa el saldo actual.
219. **No se apaga "controla inventario" con existencias** (QA INV-3): 422 "Este producto tiene existencias. Déjalas en cero con un ajuste o un conteo físico…". La importación CSV, en ese caso, deja el control encendido. Cantidades en unidad base: máximo 9.999.999.999,9999; fuera de rango (o cero en ventas, ajustes y traslados) 422 con el nombre del producto (QA INV-8).

(c) Las listas cancelan la petición anterior al filtrar o paginar (`LatestRequest`). (e) Se puede volver a elegir el mismo CSV ya corregido. (f) Los permisos de pantalla son señales (`permissionFlag`): cambian si el rol cambia sin recargar.
222. **Riesgo aceptado: costo de la venta y ajuste simultáneo** (QA INV-9): una venta toma el costo promedio vigente al bloquear el saldo; si en el mismo instante entra un ajuste con costo nuevo, la venta puede quedar valorada al promedio anterior. Las cantidades siempre son exactas (el saldo se bloquea); la diferencia es de centavos en el costo de esa venta y se corrige sola en las siguientes. Serializar también el costo haría esperar a todas las ventas del producto detrás de cada ajuste.

Todo negocio (nuevos y existentes) trae el producto **"Varios"** (SKU `VARIOS`, id fijo …0801, precio libre, sin inventario, IVA 19 %) para vender lo que aún no está creado; no cuenta para el paso "Crea tus productos" de primeros pasos. **Resumen del cierre de caja**: al cerrar una caja se envía al dueño del negocio (`tenants.owner_user_id`) un correo con ventas, anuladas, medios de pago, base, esperado, contado y diferencia, armado con el informe completo aunque cierre un cajero (el cierre ciego solo aplica a quien cierra). Ajuste `cash_close_email` (activado por defecto; un PUT sin el campo conserva el valor). El correo sale después del commit y un error al armarlo nunca impide el cierre. La entrada (/login) muestra el símbolo de XASKA arriba y centrado, con el nombre y "POS" debajo.
254. **Productos sin rotación** (pedido de la papelería: "avisar qué tiene mucho stock para sacarlo a promoción"): `GET /api/v1/reports/inventory/slow-movers?days=&branchId=` (y `.csv`, permiso `reports:read`) lista por sucursal los productos activos con inventario y existencia > 0 que no tienen ventas completadas allí desde hace `days` (7 a 365) días; los creados dentro del periodo no cuentan (no han tenido tiempo de venderse). Trae existencia, costo promedio, plata quieta (existencia × costo) y la fecha de la última venta (o "Nunca"), ordenado por plata quieta. Reportes tiene la pestaña "Sin rotación" (30/60/90/180 días, `?vista=slow&dias=`), sin periodo ni vendedor como Inventario, y las alertas del inicio avisan "$X quietos en N productos sin ventas hace 90 días" con enlace. Sin cambios de base de datos.
255. **Fiado con cupo** (Fase 10a; decisiones del usuario: solo con cupo asignado, todos fían dentro del cupo, pago mixto): el fiado es un medio de pago más, `CREDIT` ("Fiado", V19), así la venta, el tiquete, el cierre y los reportes por medio de pago lo muestran sin cambios. Solo a clientes con `customers.credit_limit` > 0 (el campo ya existía) y sin pasar el cupo; con `credit:manage` (Propietario y Administrador) se puede pasar y queda `CREDIT_LIMIT_EXCEEDED` en la auditoría. Asignar o cambiar el cupo también exige `credit:manage` (el Cajero registra clientes pero no les da cupo). Cada cliente tiene un libro inmutable `credit_entries` (venta fiada, venta anulada, abono, abono anulado; positivo aumenta la deuda) y un saldo en `credit_accounts` que se bloquea al fiar, abonar o anular: dos ventas a la vez no pasan el cupo. El bloqueo de la cuenta va al final (caja → inventario → consecutivo → cuenta) y el abono bloquea caja → cuenta. Los abonos en efectivo entran a la caja abierta de quien los recibe (`CREDIT_PAYMENT`, en el informe "Abonos de fiado") y su anulación sale de la caja (`CREDIT_PAYMENT_VOID`); por otro medio no hace falta caja. Un abono no puede ser mayor que la deuda; anular una venta fiada devuelve lo fiado y puede dejar saldo a favor, que se gasta con la siguiente compra fiada. La antigüedad (hasta 30, 31–60, más de 60 días) supone que los abonos pagan primero lo más viejo. Pantalla **Fiados** (`credit:read`): totales por antigüedad, cartera, estado de cuenta, "Abonar" (`credit:collect`: Propietario, Administrador, Cajero y Vendedor) y "Recordar" por WhatsApp (enlace `wa.me` con el mensaje y el saldo; celular colombiano con 57). En el POS, "Fiado" solo aparece con un cliente que tiene cupo y muestra lo disponible.
256. **Caja compartida** (pedido del usuario: "el admin abre la caja en la mañana y se cierra en la noche"; decisiones: opción por caja, cierra quien la abrió o un admin, los demás registran ingresos y egresos pero no retiros): cada caja es **compartida** o **personal** (`cash_registers.shared`, V20). En una compartida una persona abre la sesión con la base y los demás de la sucursal se **unen** (`POST /cash/sessions/{id}/join`, tabla `cash_session_users`): sus ventas, abonos y anulaciones usan esa sesión (`lockOpenOf` busca la propia y, si no hay, la compartida a la que se unió) y cada venta conserva quién la hizo. Quien tiene su propia caja abierta no se une a otra; abrir la propia o unirse a otra deja la anterior; al cerrarse la sesión todos quedan sin caja. Solo quien la abrió o quien tiene `cash:audit` la cierra y registra retiros (el cierre ciego no cambia). Quien vende sin `cash:operate` puede unirse (`sales:create`). La CAJA-1 sembrada pasa a compartida en todos los negocios (en uno pequeño hay un solo cajón); las cajas nuevas son personales salvo que se marquen. POS y Mi caja muestran "Vender en CAJA-1 (abierta por …)" y "Dejar esta caja" (Mi caja exige `cash:operate`: un rol personalizado solo con `sales:create` se une desde el POS pero no tiene "Dejar esta caja" ni movimientos). Si la caja vuelve a ser personal, los que se unieron dejan de vender en ella; el acceso a la sucursal se revisa al unirse (como al abrir). Si al cobrar la caja ya se cerró, el POS vuelve a la apertura sin perder el carrito.
257. **Ajustes de seguridad del fiado y la caja compartida** (QA del 2026-10-19, `docs/QA.md` §7): unirse, dejar y abrir caja se serializan por usuario (bloqueo de su fila en `members`), así nadie queda en dos cajas; egresos y retiros bloquean la sesión en exclusiva para no sacar entre dos más efectivo del que hay; quien se unió solo cuenta mientras la sesión esté abierta y la caja siga compartida, y ve solo sus propios movimientos (el cierre ciego se conserva); unirse revisa primero la sucursal (403 sin datos de la caja); dejar una caja queda en la auditoría (`CASH_SESSION_LEFT`). Un abono sin caja abierta solo lo registra quien tiene `credit:manage` (así todo abono de un cajero o vendedor queda en un cierre). El cupo se lee con la cuenta bloqueada y, sin cupo, solo se fía contra un saldo a favor.
258. **Pedidos por encargo** (Fase 10b; pedido de una empresa de mármoles y granito; decisiones del usuario: por m² y por pieza, se vuelve venta al entregar, entregas parciales por ítem, fecha de entrega con aviso de vencidos, comprobante para el cliente, dirección opcional; sin estados de producción): un pedido (`orders`, V21, consecutivo `PED`) es un compromiso con un cliente registrado (no el Consumidor final): líneas con un producto del catálogo (puede ser uno genérico o "Varios"), descripción, cantidad o medidas (ancho × largo en metros; la cantidad es el área a 4 decimales y la unidad base del producto debe aceptar decimales, se siembra **M2**), precio acordado y total calculado como en la venta. No mueve inventario ni ingresos. Los **anticipos** van a un libro inmutable `order_payments` (anticipo +, devolución −, aplicado −, entrega anulada +; lo disponible es la suma) y en efectivo entran a la caja el día que se reciben (`ORDER_PAYMENT`, "Anticipos de pedidos" en el informe; devolución `ORDER_REFUND`). Sin caja abierta solo registra un anticipo quien tiene `orders:manage`. Lo anticipado nunca pasa de lo que falta por pagar, y una edición no puede dejar lo pendiente por debajo del anticipo. **Entregar** (todo o parte de las líneas pendientes) registra una venta normal con los precios acordados y el nombre "Producto · descripción" (`SaleService.createForOrder`): el anticipo disponible se aplica con el medio de pago **Anticipo** (`DEPOSIT`, …0705, no entra al efectivo, no se puede elegir en el POS) y el resto se paga como en el POS (efectivo con cambio, transferencia, fiado…). La clave de idempotencia es la de la venta. Si una entrega completaría el pedido dejando anticipo sin aplicar, se rechaza (hay que revisar los precios o cancelar lo pendiente). **Anular** la venta de una entrega devuelve esas líneas a pendientes, reversa lo aplicado y reabre el pedido (si ya estaba cancelado sigue cancelado y aparece "Devolver anticipo"). Solo se aplica como Anticipo exactamente lo que el pedido descuenta (la venta lo valida), y ese medio no sirve para pagar el resto ni para abonar un fiado. Si desde que se hizo el pedido cambió el impuesto del producto o "precios con IVA", la entrega se rechaza hasta editar el pedido: nunca se cobra distinto de lo acordado sin revisarlo. **Cancelar** (`orders:manage`) cierra lo pendiente y devuelve el anticipo disponible con un medio elegido (en efectivo, con caja abierta). Bloqueos: venta → caja → pedido → inventario → consecutivo → cuenta de fiado. Permisos (V21): `orders:read` (Propietario, Administrador, Cajero, Vendedor, Contador), `orders:create` (crear, editar, anticipos y entregar; Propietario, Administrador, Cajero, Vendedor; entregar exige además `sales:create`), `orders:manage` (Propietario, Administrador). Pantallas: **Pedidos** (por entregar, atrasados, para hoy, falta por cobrar; filtros y búsqueda), editor (cliente, fecha, dirección e indicaciones opcionales, líneas por cantidad o por medidas con total estimado), detalle (entregar, recibir anticipo, editar, cancelar, comprobante imprimible en la impresora del tiquete y por WhatsApp con el detalle, lo abonado y lo que falta) y un aviso en el inicio con los atrasados y los de hoy. Un pedido atrasado sigue abierto y se puede editar sin moverle la fecha: el aviso es solo informativo.
259. **Ticket del cierre de caja** (pedido del usuario; decisiones: ticket térmico, enviar por WhatsApp, reimprimir): el informe de caja (cierre Z o parcial X) se abre en un diálogo con "Imprimir ticket" (mismo papel de 58/80 mm y logo que el tiquete de venta, con línea de firma) y "Enviar por WhatsApp" (resumen en texto, `wa.me` sin número para elegir el contacto). Solo frontend: usa el mismo `GET /cash/sessions/{id}/report`.
260. **Cotizaciones** (Fase 10c; pedido de la marmolería, la papelería y ventas al por mayor; decisiones del usuario: se convierte en pedido o en venta, para un cliente o un prospecto, vigencia por defecto en Ajustes, descuento por línea, condiciones y notas, PDF con logo; sin desglose de impuestos): `quotes` (`COT-n`) con estado `OPEN`, `ACCEPTED` (convertida; guarda `converted_type` ORDER/SALE y el id) o `REJECTED` (con motivo); "vencida" no se guarda: es abierta con `valid_until` anterior a hoy en la zona del negocio. Para un **prospecto** basta el nombre (y teléfono para WhatsApp); al convertir en pedido se exige registrarlo como cliente (queda asignado), en la venta es opcional (si no, Consumidor final). Las líneas son las del pedido (cantidad o ancho × largo en M2) más `discount_percent`; el total se calcula como en la venta (`SaleCalculator`) y la regla del descuento máximo (`sales:discount`) se aplica al cotizar, así lo cotizado se puede vender sin sorpresas. **Vigencia**: `quote_validity_days` (15) y `quote_terms` en Ajustes, editables en cada cotización; una vencida no se convierte (422): se renueva editando la fecha (y revisando precios) o se duplica (`?desde=id` en el editor, solo frontend). **A pedido**: mismas líneas y medidas con el precio neto de descuento (el pedido no maneja descuentos; el total puede variar unos pesos por redondeo). **A venta**: `SaleService.createForQuote` con `agreedPrices` (precio cotizado, sin `PriceChanged`), nombres "Producto · descripción", idempotente con la clave de la venta. Orden de bloqueo: cotización → (pedido) → caja → existencias → consecutivo. El PDF es una hoja imprimible (logo, nombre comercial, dirección y teléfono de la sede activa más antigua, líneas, total, vigencia, notas y condiciones; "no es factura") que se guarda como PDF desde el diálogo de impresión, sin generar archivos en el servidor. Permisos `quotes:read` (también Contador) y `quotes:create` (Propietario, Administrador, Cajero, Vendedor). Como en el pedido, el precio de cada línea es el que se escribe (sin `sales:open-price`); solo el descuento tiene tope. Si después se cancela el pedido o se anula la venta, la cotización sigue aceptada (apunta a ese documento): para volver a ofrecerla se duplica. `business_settings.setting_value` pasa a 1000 caracteres por las condiciones.
